# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Java 25 program that embeds CPython through the FFM API, using bindings generated by jextract from `Python.h`. No JNI glue, no C to compile. Any libpython **3.12 or later** works, chosen at startup; the code switches on the loaded version where newer CPython APIs matter. It's tested on Linux with 3.12, 3.13, 3.14 and 3.15. `README.md` is the detailed reference; this file is the orientation.

## Commands

Work inside the Nix dev shell (`nix develop`). It provides JDK 25, jextract, `python3` (3.12) and `python3.13`–`python3.15`, and Gradle without downloads.

```sh
./gradlew build run                                     # build, test, run Main against python3
./gradlew run -q -Ppython.executable=python3.14         # pick the libpython (any interpreter, or a venv's python)
./gradlew run -Ppython.library=/path/libpython3.X.so    # or a library directly (no venv support then)
./gradlew test -Ppython.executable=python3.15           # tests against another version
./gradlew test --tests '*SubInterpreterTest'            # one class
./gradlew test --tests '*SubInterpreterTest.ownGilRunsInParallel'   # one method
./gradlew test --rerun ...                              # tests are cached; --rerun forces them (it applies to the task just before it)
./gradlew jextract                                      # regenerate all bindings (7 tasks); e.g. ./gradlew jextractStable312 for one
```

- **Verify a change against the whole version matrix,** not just 3.12: run `test -Ppython.executable=python3.1X` for 12 to 15.
- **Tests always embed a venv** (`build/test-venv`), created from `-Ppython.executable`.
- **There's no separate lint step.** `javac` runs with `-Xlint:all,-restricted -Werror`, so warnings fail the build.
- **jextract (nixpkgs build) intermittently segfaults inside libclang;** just rerun it. A failed or crashed run never touches the committed bindings. `--dump-includes` on the full `Python.h` crashes most of the time.

## Architecture

Three layers, with strict boundaries between them.

**1. Generated bindings: `src/main/jextract/` (committed; never edit by hand).** Regenerate with `./gradlew jextract`. Each `jextract/*.symbols` file is a jextract argument file, and each feeds one task and one package:

- **`capi.stable312.Stable312`:** the Stable ABI at the 3.12 level (`Py_LIMITED_API=0x030C0000`). Almost everything comes from here.
- **`capi.stable313` / `stable314` / `stable315`:** only what the Stable ABI *added* at that level (e.g. `PyImport_AddModuleRef`, `Py_TYPE`, `Py_IS_TYPE`).
- **`capi.py312.CPython312`, `capi.py314.CPython314`:** non-Stable-ABI API from the full headers of exactly that version (sub-interpreter config structs, `PyConfig_Get`). Only symbols whose declarations and layouts are identical in every supported version may go here.
- **`dlfcn.Dlfcn`:** libc's `dlopen`, not Python.

The build enforces two things for these tasks:
- **Exact header versions:** each Python task fails unless `jextract.python3XX` (in `gradle.properties`) points at exactly that version.
- **Every listed symbol is generated:** the task fails if any `--include-*` line produced nothing, because jextract skips unbindable symbols silently or with buried warnings.

The task and plugin live in `build-logic/` (`JextractTask`, `JextractPlugin`).

**2. Typed internal layer: `com.example.ffm.python.internal` (not exported).** The only code allowed to call CPython functions that take or return objects, thread states or interpreter states.
- **`PyObject`:** a sealed interface over records wrapping a `MemorySegment` (`Any`, `Code`, `Dict`, `List`, `Module`, `Str`, `Type`). Each CPython function lives on the record it applies to (`module.dict()`, `code.eval(...)`, `obj.getAttr(...)`, `obj.call(...)`). `PyThreadState`, `PyInterpreterState` and `GilState` are records for the non-refcounted handles. Records reject `NULL`.
- **Ownership is in the types.** A bare record is a **borrowed** reference: never release it. A `NewReference<T>` is **owned**: use try-with-resources; `close()` does `Py_DecRef` exactly once. Wrappers return whichever CPython documents for that function. Anything borrowed from a container Python code can change (`sys.modules`, `sys.meta_path`, list items) must be promoted with `NewReference.incRef` before running Python code, or returned as a `NewReference` (as `Module.importAddRef` does).
- **Version dispatch:** `ApiLevel.atLeast(3, N)` reads the loaded library's `Py_Version`. **Every call into `stable313`/`314`/`315` or `py314` must sit behind such a check.** jextract resolves symbols lazily, so the bindings are harmless on older libpythons until called. `HeaderInlines` holds functions that were header-only `static inline`s before being exported (`Py_TYPE`, `Py_IS_TYPE`), each with a fallback built from older exported functions, never from struct layouts. `Configuration` (`Py_Get*()` up to 3.13, `PyConfig_Get` from 3.14) and `Module.importAddRef` are the other dispatch points.
- **Version-specific wrappers** stay in `Py312` / `Py314`. The records use only the Stable ABI.

**3. Public API: `com.example.ffm.python`.**
- **`EmbeddedPython`** is the main interpreter: `start`, `exec`, `version`, `configuration`, `interpreterInfo`, `findExtensionModule`, `newSubInterpreter*`, `close`. Plus `SubInterpreter`, `InterpreterConfig`, `InterpreterInfo`, `PythonVersion` and `PythonException`.
- **`LibPython`** (package-private) finds and loads libpython at startup:
  - which library: `-Dpython.library`, or a `sysconfig` query of `-Dpython.executable`;
  - it re-`dlopen`s the library `RTLD_GLOBAL`, without which C extension modules fail with "undefined symbol";
  - it checks for ≥ 3.12;
  - it hands `Py_SetProgramName` the interpreter's `sys.executable`, which is how venvs work.
- **`Main`** is the demo. It optionally `System.load`s jpy's extension (found with `findExtensionModule`) before importing it.

## Rules that are easy to break

- **Threads and the GIL.**
  - `EmbeddedPython` is confined to its starting thread, and holds the main GIL only during each call. Use `threadState.runAttached`/`callAttached`, never hand-written attach/detach.
  - A `SubInterpreter` is confined to the platform thread that created it; virtual threads are rejected.
  - Close sub-interpreters before the main interpreter.
- **Validate every `InterpreterConfig`** in Java before CPython sees it: on 3.12, a config CPython rejects leaves the GIL released and the process aborts on the next GIL operation.
- **One CPython per process.** CPython can't be re-initialized, so the test task uses `forkEvery = 1`: each test class gets its own JVM and starts one `EmbeddedPython` (in `@BeforeAll` for multi-test classes). Tests that need the internal layer attach with `GilState.ensure()` / `release()` (see `HeaderInlinesTest`).
- **To bind a new C function:**
  1. Add it to the right `.symbols` file, at the lowest Stable ABI level that has it.
  2. Run `./gradlew jextract`.
  3. Add a typed method on the matching record, with the right ownership.
  4. If it's newer than 3.12, add an `ApiLevel` guard and a fallback.

  Function-like macros can't be bound; bind the function behind them (e.g. `Py_DecRef` for `Py_DECREF`).
- **Python output isn't in `System.out`.** Python writes to native stdout, which is buffered until finalization when it isn't a terminal. Flush (`sys.stdout.flush()`, `flush=True`) when ordering against Java output matters, and don't grep demo output assuming Java's line order.
- **Gradle and `PATH`:** commands named in the build (`jextract`, `python3.X`) are resolved against the invoking shell's `PATH` (`executableOnPath` in `build-logic`), because the Gradle daemon's own `PATH` goes stale across Nix shells. Keep using that helper for new command-name lookups.
